# OpenCode V2 Implementation Plan

> **For agentic workers:** Execute with superpowers:executing-plans, verifying each stage before proceeding.

**Goal:** Upgrade the image and this running instance to OpenCode 2.2.1 safely.

**Architecture:** Pin the V2 CLI package and run its foreground server. Rehearse
against copied state, then use a sibling container for transactional cutover and
offline-state rollback.

**Tech Stack:** Ubuntu 24.04, npm, GitHub Actions, GHCR, Podman API, Node.js.

## Global Constraints

- OpenCode 2.2.1, non-root UID/GID 1000, existing persistent mount paths.
- No software installation in the running development container.
- Never log credentials or overwrite unrelated user changes.
- Do not expose an unauthenticated API or migrate the only copy of V1 state.

### Task 1: Image and Publishing

Files: `Dockerfile`, `compose.example.yml`, `.github/workflows/publish.yml`,
`tests/image.test.mjs`, `README.md`, `MIGRATION.md`.

- [ ] Add Node tests asserting the pinned V2 package, foreground `serve`, and
  explicit port 4096. Run `node --test tests/image.test.mjs`; expect failures.
- [ ] Add `ARG OPENCODE_VERSION=2.2.1` and install
  `npm install -g "@opencode/cli@${OPENCODE_VERSION}"` in the Dockerfile.
- [ ] Change example entrypoint to `opencode serve --hostname 0.0.0.0
  --port 4096`, retaining CORS and password passthrough.
- [ ] Build/load the image in CI, run version/user/serve-help smoke checks,
  then publish the same build using Buildx caching.
- [ ] Document V2 package, server, auth, rehearsal, backups, and rollback.
- [ ] Run regression tests and `git diff --check`, review, then commit only
  upgrade files and push to main without force.

### Task 2: Configuration and Rehearsal

Files: protected migration files under the live Compose directory; global
`opencode.jsonc`, `AGENTS.md`, and five agent definitions.

- [ ] Copy config/state and back up SQLite consistently to restricted staging.
- [ ] Keep V1 syntax; replace unavailable model IDs with catalogued IDs using
  existing authenticated providers. Use strong reasoning for planning/review,
  efficient exploration/research, and a coding model for implementation.
- [ ] Verify Superpowers' default export has `id` and `setup`, and pin the tested
  revision. Update tool-name guidance for V2 without weakening permissions.
- [ ] Start V2 on copied state without proxy labels. Require API auth failure
  without credentials and successful version, session, model, agent, plugin,
  skill, and MCP checks with credentials. Preserve existing session history.

### Task 3: Transactional Cutover

Files: protected sibling-helper script and status under live Compose directory.

- [ ] Pull the published immutable image; run its non-root/version smoke check.
- [ ] Capture old container settings in memory and construct equivalent V2
  settings with the new image, `serve`, explicit port, and existing password.
- [ ] Start a detached sibling helper with explicit host mounts and socket.
- [ ] Helper stops V1, backs up config/data/state offline, preserves V1 under a
  rollback name, applies tested configuration, and starts V2 under canonical name.
- [ ] Helper verifies API auth, version, historical sessions, and stabilization;
  on failure restore offline state and original Compose and start V1.
- [ ] Keep backups and the V1 container; write only non-secret result status.
